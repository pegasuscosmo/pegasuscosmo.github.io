N-Body Simulations

Simulating how large numbers of bodies pull on each other under gravity — from a first pure-Python attempt to a GPU-parallel version handling millions of particles.

  1. N-Body Sim

    Python · Barnes–Hut Algorithm · Velocity Verlet

    My first version: randomly generated bodies pulling on each other under gravity, using the Barnes–Hut algorithm to cut down on calculations and velocity Verlet integration for accuracy. Quickly put together and not at all optimized — but it worked, and it's what taught me the algorithm.

    Code ↗

  2. Barnes–Hut N-Body (Optimized)

    Python · Taichi (GPU) · Custom Parallel Radix Sort

    A full rebuild for parallelism: up to 2,000,000 particles in real time by encoding positions as Morton codes, sorting them with a radix sort I wrote myself, and building the Barnes–Hut tree directly from the sorted codes on the GPU every frame. Includes density, velocity, and hybrid visualization modes, plus recording to 60fps MP4.

Planetary Ring Simulations

Modeling how moons gravitationally sculpt planetary rings — three passes, each more physically accurate or more scalable than the last.

  1. Ring Sim

    Python · Velocity Verlet

    Simulates moons' gravitational effect on ring particles with stable orbits, time warp, random generation/resets, trajectory drawing, and interactive body creation — click and hold to spawn a body, then tune its mass, size, and velocity before releasing it into the system.

    Code ↗

  2. Ring Sim 2

    Python · Taichi (GPU)

    A remake using Taichi for GPU parallelism, supporting far higher particle counts, with a revamped UI and run-time editing of the simulation parameters.

    Code ↗

  3. Saturn Ring Sim

    Python · Taichi (GPU) · Wisdom–Holman Integration

    Models Saturn's actual rings using Wisdom–Holman symplectic integration — propagating Kepler orbits with Lagrange coefficients for extreme long-term orbital stability — plus statistical particle-particle collisions and a live plot of radial ring density.

Dev Story · N-Body Simulations

How I Broke (and Fixed) a 2-Million-Particle Galaxy Sim

I started making N-body sims after watching Deadlock's video on the Barnes–Hut algorithm. My first attempt was pure Python: an object-based tree built with recursive division. It was incredibly slow, and the high theta I needed just to get playable performance introduced a lot of visual artifacts.

After discovering Taichi, I took a more parallel approach. A lot of the later work happened in my AP Computer Science Principles class, for the AP performance task. I built a binary radix tree, since it's friendly to both storage and speed — it can be constructed entirely in parallel and always has exactly 2N−1 nodes, which mattered because Taichi's dynamically sized fields are extremely slow. Getting there needed sorted Morton codes, and after failing to write my own radix sort a few times, I fell back on Taichi's built-in parallel_sort().

From there, computing forces was relatively easy. I added a density-based visualizer by accumulating a value into each pixel a particle occupied (and its neighbors), then mapping that to brightness and color. At around 100,000 particles at 20fps, I submitted it for the AP Performance Task.

I then took a break to build Ring Sim 2 for a game jam. In late July I came back, unsatisfied with the performance — largely because Deadlock's video showed a simulation running millions of particles. Profiling showed the Morton-code sort I was using — a modified even-odd sort with 190 serial stages — was taking hundreds of milliseconds at high N. So I went back to writing my own radix sort. This time it worked: ~26ms to sort N=1,000,000. Plugged into the sim, I was now running 500,000 particles at a solid framerate.

Encouraged, I pushed for more. At N=1,000,000, gravity just… turned off. No errors, no visible NaNs, nothing wrong in the force or tree code that I could find. I let it sit for a while.

When I showed my family the simulation, my sister asked how far I could push it. When I said something broke at 1,000,000, she suggested we find the exact number. A manual binary search later, we had it: N = 809,551.

Digging in, I found a NaN in the root node's mass, traced down to a child with a NaN'd position. It turned out Taichi's random() is deterministic — the same seed and parameters always place a given particle in the exact same spot. At exactly N=809,551, it happened to return (0, 0) for one particle's position. A faulty while loop check let that slip through, putting a particle exactly at the center. Computing its velocity meant dividing by its distance from center — zero — which produced a NaN that infected the whole tree: every center-of-mass comparison involving that node returned false, which, in effect, turned gravity off.

A second bug showed up once I gave galaxies their own bulk velocities: their cores were pinned in place, unable to move. The cause was a Verlet position half-step happening after the tree was built each frame, letting particles (and even galaxy cores) gravitate toward their own past positions — and in a dense enough region, that overpowered every other force. Moving the half-step to before tree construction fixed it.

After all that, I broke the 1,000,000-particle barrier. It now runs at roughly 15fps with N=2,000,000, with frame time scaling close to the expected O(n log n) (see the curve fit). I learned a lot along the way — parallel algorithms, working directly with the GPU, and more about how 2D gravity actually behaves than I expected going in.
